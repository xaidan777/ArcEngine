# ArcEngine / Blackwater Protocol — full engine + game audit

Date: 2026-09-19. Scope: engine (`js/World3D.js`, `js/Terrain3D.js`, `js/Location3D.js`,
`js/Model3D.js`, `js/Gltf3D.js`, `js/CameraControl.js`, `js/engine/*`), game
(`js/Game.js`, `js/RaidRules.js`, `js/ShooterRules.js`, `js/MenuSystem.js`, `js/audio/*`,
`js/WeatherSystem.js`, `js/DayNightCycle.js`), assets, tooling and tests.

Method: six parallel read-only audits (render/shaders/texturing, performance, physics,
FPS gameplay readiness, assets, runtime bugs) plus independent measurement on this machine:
headless Chrome over CDP (no npm installs), pure-Node GLB parsing, `node --test`, and
`tools/benchmark-engine.mjs`. Every number below was measured, not inferred, unless marked
otherwise. Nothing in the repository was modified by the audit.

## 2. Engine verdict

The rendering **content** is well above average for a no-dependency kit: real PBR materials
with albedo/normal/roughness maps, a 2K HDR skybox, ACES tone mapping, merged static
architecture, thin-instanced grass, freezeWorldMatrix on props, a working toon plugin, a
deterministic fixed 60 Hz simulation step, and a genuinely good procedural Web Audio synth
stack. The **plumbing** is what fails: the whole layer named "ArcEngine" in the docs is not
wired to the game, post-processing is unconditional and out of budget, and shadows are
computed but never visible.

### 2.1 `js/engine/*` is dead code in the shipped game (P0)

`ArcEngine` is instantiated only as a module-level singleton (`js/engine/ArcEngine.js:354`).
Nothing calls `ArcEngine.init`, `createScene`, `update` or `startLoop`; `js/main.js` never
imports it, and `js/Game.js` contains zero references to `ArcActor`, `ArcSpatialGrid`,
`ArcStateMachine`, `ArcEngine`, `ArcEventBus`, `ArcInspector` or `ArcPostProcess`.

Two files are not even loaded: `js/engine/ArcEventBus.js` and `js/engine/ArcStateMachine.js`
have no `<script>` tag in `index.html` and no line in `CODE_FILES`
(`tools/asset-scan.mjs:27`), yet they are the ones the tests exercise. Adding the missing
`<script>` tags is not sufficient: `ArcEventBus` is declared twice as a top-level lexical
`class` (`js/engine/ArcEngine.js:12`, `js/engine/ArcEventBus.js:377`), so loading both throws
`SyntaxError: Identifier 'ArcEventBus' has already been declared` in either order. The
duplicate must be removed (or renamed) and the file registered.

This is also why `ENGINE_API.md` §2.1 is aspirational: `ArcEngine.init({...})` returns an
instance, not a promise, so the documented `await` + `loadScene` + `start` ten-liner cannot
work as written.

### 2.2 Shadows are computed and invisible (P0)

`WORLD3D_TOON = 0` (`js/Constants.js:159`). The only thing that reintroduces Babylons's
shadow darkening is `ArcToonPlugin` (the `ARCSHADOW` define), and the plugin is registered
for `StandardMaterial` only (`js/World3D.js:699`). The shadow generator itself runs with
`darkness = 0` (`js/World3D.js:834`), and Babylon's shader does
`shadow = mix(darkness, 1.0, shadow)`, so `darkness = 0` means "a shadow multiplies light by
1.0". Consequence:

- 78 `StandardMaterial` surfaces carry the plugin and would be shadowed, but the plugin is
  compiled with `ARCTOON = false` and `ARCSHADOW = true`, which only tints; the band math is
  skipped. Net effect on the frame: none.
- 64 `PBRMaterial` surfaces (`RaidEnvironment.surface()`, the district, the weapon viewmodel)
  never get the plugin at all and therefore can never be darkened.

Measured directly: with all 243 shadow casters removed from the render list the frame is
byte-identical (same md5). The 2048² shadow pass is paid in full for zero visible result.
The `dead` shadow also means the district does not react to the sun at all, which is the
single largest reason the scene reads as "flat and grey".

### 2.3 The post-process stack is unconditional and dominates the frame (P0)

`Game.setupAtmosphere()` (`js/Game.js:171-225`) builds, on every desktop start:
SSAO2 (half-res + blur), `DefaultRenderingPipeline` (FXAA + grain + sharpen), a GlowLayer,
ACES + vignette on the image-processing configuration, and a 280-particle dust system. Nine
post-processes are attached to the camera. There is no budget, no resolution scaling tied to
the GPU, and the whole stack is created before the first frame.

Toggle measurements (960x540, SwiftShader, so treat as directional):

| State | avg frame |
|---|---|
| baseline | 365 ms |
| HUD hidden | 355 ms (HUD is not the cost) |
| ink/outline off | 357 ms (already off) |
| shadow casters cleared | 336 ms |
| hardware scaling 1/2 | 223 ms |
| hardware scaling 1/4 | 134 ms |
| **scene.render() disabled (CPU only)** | **16.6 ms** |

CPU work per frame is ~16.6 ms (JS logic + HUD + DOM). Everything else is GPU/fill. That is
the correct order of attack: pixel cost first, then draw calls, then CPU.

### 2.4 Draw calls: 2119 per frame at 9 active meshes (P0)

Babylon's `_drawCalls.current` accumulates; sampling it in `onBeginFrameObservable` across six
consecutive frames gives a strictly linear +210 per frame (2119, 2329, 2539, 2749, 2959,
3169). Meanwhile `getActiveMeshes().length` is 9 and `scene.meshes.length` is 313. The
active-mesh evaluation is near-degenerate, and per-frame draw state changes are far above
what a 313-mesh scene needs. Contributors found in the code:

- 9 enemies each build 11+ meshes with three **per-index** materials
  (`drone-armor-<i>`, `drone-joint-<i>`, `drone-eye-<i>`, `js/Game.js:721-724`) — 27 materials
  where 3 would do, defeating batching.
- The procedural weapon viewmodel is ~40 separate `createBeveledBox` meshes in rendering
  group 3 (`js/Game.js:227-345`), each with `alwaysSelectAsActiveMesh`.
- Tracers, casings, sparks, decals and impact discs are created and disposed per shot; the
  tracer material is created per shot (`js/Game.js:1812`) and only the mesh is disposed on
  hit/expiry (`js/Game.js:3070,3073`) — a per-bullet `StandardMaterial` leak.
- Nine post-processes are full-screen passes at 1280x720.

### 2.5 Physics and collision: a hand-maintained circle list (P0 for FPS)

There is no physics engine and no rigid body anywhere in `js/engine/` (`ColliderComponent`
is a static cylinder test with no velocity, gravity or mass). What exists is a coherent,
pure, already-tested analytic layer in `js/ShooterRules.js`: swept segment-vs-circle,
`resolveCircleMovement` (2D slide), `rayCylinderHit` (3D vs vertical cylinder with caps),
`stepProjectile` (gravity + drag + swept tests vs actors, blockers and terrain).

The world geometry for collision is `this.blockers` / `this.coverBlockers`
(`js/Game.js:541,549`) — about 40 hand-written 2D circles plus 44 from
`RaidEnvironment.obstacle()`. Consequences:

- **Walls, roofs and interiors do not exist for collision or for bullets.** The 250x340x1220
  factory box (`js/RaidEnvironment.js:174`) is not a blocker; you walk and shoot through it.
- **No actor-vs-actor collision** — enemies and the player interpenetrate.
- **Jump is cosmetic**: `tryJump`/`updateJump` (`js/Game.js:1564-1587`) write
  `this.jumpOffset`, but the camera reads `player.jumpOffset` (`js/CameraControl.js:623`),
  which is initialised to 0 (`js/Game.js:520`) and never written. Measured: jump arc reaches
  33.8 px in the logic, camera offset stays 0. The jump also drains
  `this.stamina.current`, but the stamina object uses `.value`, so the drain silently
  produces `NaN` on a field nobody reads (`js/Game.js:1571`).
- **No step-up, slopes, fall damage, crouch, lean or vault.**
- **No penetration, ricochet, limb hitboxes** — one cylinder plus a 22 % head band.
- **Explosions ignore walls** (flat 2D radius falloff).
- **Server authority is a mirage**: `server/simulation.mjs` re-runs the same rules in
  `node:vm`, but it is flat (`h` stays 0, no `heightAt` passed to `stepProjectile`), it
  simulates no enemies/loot/objectives, and `js/RaidClient.js` is instantiated only in tests.
  The browser never connects.

## 3. Visual pipeline: what is missing to look good

**Present today:** PBR albedo/normal/roughness on the district surfaces
(`js/RaidEnvironment.js:82-105`), triplanar-ish UVs for beams (`:285-304`), one 2K HDR
environment cube with a procedural 32² fallback, `createDefaultSkybox`, ACES + vignette,
SSAO2, glow, grain, sharpen, FXAA, a dust particle system, per-group specular, a toon
`MaterialPluginBase` with bands/spec/rim (currently off), ink edges and silhouette outlines
(currently off), one 2048² shadow map with a camera-fitted ortho frustum.

**Missing / broken, in order of visual return:**

1. **Shadows that darken** (§2.2). Nothing else matters until this is fixed — it is the
   difference between "flat grey plane" and "lit space".
2. **PBR is outside the shader language.** 64 PBR materials get no toon, no colored shadow,
   no ink, no outline, while 78 Standard ones do. Two incompatible lighting models in one
   frame. Babylon's shipped GLSL contains the same `aggShadow=aggShadow/numLights;` anchor
   inside the PBR shader (verified in `libs/babylon.js`), so a twin `MaterialPluginBase` for
   `PBRMaterial` is a small, well-founded change.
3. **A ground that is one tiled texture.** `js/Terrain3D.js:64-96` copies a 512 px JPG into a
   `DynamicTexture` and repeats it 8x over 4096 px; `RaidEnvironment.setupGround` swaps in one
   mud PBR set at repeat 16 and shares it with the outer ring (wrong UV scale there). No
   splat/blend, no slope mask, no macro/detail map — the single biggest "tiled wallpaper"
   tell at ground level.
4. **Effects that are untextured primitives.** Bullet marks are `disableLighting` discs
   (`js/Game.js:1910`), sparks are `CreateLines`, casings are tiny cylinders, the muzzle flash
   is an emissive cone with **no light**, and there are no decals, no blood, no smoke, no
   muzzle-flash point light, no tracer trails. `BABYLON.CreateDecal`, `TrailMesh` and
   `VolumetricLightScatteringPostProcess` are all present in the vendored build and unused.
5. **Material fidelity lost on GLB load.** `Gltf3D._standard` (`js/Gltf3D.js:109-128`) drops
   metallic/roughness, `metallicTexture`, reflection/IBL, `emissiveTexture`, `ambientTexture`
   (AO), `opacityTexture`, lightmap, parallax and `bumpTexture.level`. Emissive optics and
   screens simply disappear in toon mode.
6. **Shadow strategy.** One ortho frustum refit **every frame** from
   `CameraController._apply` (`js/CameraControl.js:663-665`), calling `computeWorldMatrix()`
   on every shadow caster each frame (`js/World3D.js:909`). `CascadedShadowGenerator` is in
   the build and unused.

## 5. FPS gameplay readiness

Verified working (not scaffolding): deterministic fixed-step logic at 1/60 with a 6-substep
clamp; 3D ballistic projectiles with gravity, drag, falloff and headshots; layered
shield -> HP damage with recharge; ADS + recoil spring + weapon sway + camera kick; magazine
reload with staged audio; 155 `UILayout.js` records with all ~60 `UI.get` ids in `Game.js`
resolving; a real pre-raid meta layer (dispatcher gate, four traders, workshop crafting,
settlement with safe pockets); ~45 live procedural-audio call sites; day/night and weather
systems (weather currently dead, §2.6).

Verified missing or broken:

- No crouch/prone/lean/vault/fall damage; head bob absent; jump cosmetic (§2.5).
- Fire modes absent; `fireRate` (RPM) is **never read** in `Game.js`, so all 19 weapons fire at
  one shared 0.16 s interval (`js/Game.js:1668`).
- No grenades and no melee; the EMP grenade exists as item + recipe only.
- Enemy perception is a 360° LOS circle (`js/Game.js:2227`); no vision cones, no pathfinding
  (direct steering only), no navmesh.
- Two archetypes (`scout`, `heavy`) and the reinforcement wave are unreachable:
  `GAME_ENEMY_COUNT = 9` while the mapping chain claims every index 0..8, and
  `dormant: i >= 14` (`js/Game.js:916-932`).
- `ARC_MACHINE_TYPES` is referenced 0 times in `Game.js`; HP/radius live in hardcoded
  ternary chains that have already drifted.
- Weapon viewmodel is a procedural box rifle; `preloadCricketModel`/`preloadScreamerModel`/
  `preloadRubezhModel` have no call sites, so 5 of 9 spawned enemies and the held weapon are
  placeholders while ~45 MB of skinned models sit unused.
- Measured combat: hits **do** register against tracking targets (20 shots -> 3 hits, kill),
  but accuracy is ~15 % because the projectile starts at eye + muzzle and the target moves;
  measured time-to-death while idle inside the spawn area is > 240 s (nearest enemy 677 px,
  aggro 480), so there is no early pressure.
- Full objective loop verified end-to-end: 3 pickups -> `extractState = available` -> `E` at
  the beacon -> `inbound` (15 s) -> `boarding` -> `finish(true)` -> result panel.

## 7. Risks and things not to do

- Do not "just add the script tag" for `ArcEventBus.js`/`ArcStateMachine.js` — the duplicate
  top-level `class` makes the page throw (proven). Remove or rename one first.
- Do not load `rubezh76_tier4.glb` as-is: it needs a meshopt decoder, and Babylon's default is
  a CDN fetch, which breaks invariant 1. Re-export it first.
- Do not enable `WORLD3D_TOON` together with `WORLD3D_TOON_OUTLINE` for looks: the outline
  path builds `HighlightLayer`s per kind x group and depends on the private
  `_thinEffectLayer._options` field and on `stencil: true`; the code comments already record
  a case where the blur chain emptied and the outline vanished.
- Do not convert GLB models to `InstancedMesh` for performance: instances share one material,
  which breaks the current per-material toon group and the ink/outline registration.
- Do not raise `maxSimultaneousLights` blindly — each light costs a uniform block per
  material, and the sun must stay the **last** light or the coloured-shadow reconstruction
  reads the wrong light.
- Do not touch `scene.imageProcessingConfiguration.applyByPostProcess`: it is scene-global and
  shared by the DRP, the standalone image-processing pass and every material plugin.
- Mobile is already cheaper by design (1024² shadow map, halved radius, the entire SSAO/DRP/
  glow/dust stack skipped, hardware scaling capped at 1.5x). Preserve that split when moving
  the post-process stack behind constants.
