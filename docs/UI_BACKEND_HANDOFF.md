# Blackwater: зависимости UI от серверной части

Дата: 2026-09-20. Статус: задачи для backend-разработчиков, не реализованы в этом UI-проходе.

## Источник истины

Онлайн-баланс и агрегированная статистика берутся из `GET /account`, через `RaidClient.refreshAccount()`. Клиент не должен рассчитывать награду, списывать валюту, выдавать ресурсы или завершать серверные таймеры. Локальные каталоги допускаются для описания предметов и предварительного просмотра, но не являются подтверждением владения.

Текущий ответ аккаунта содержит `credits` и `stats` (raids, extractions, kills, deaths). В нём нет ядер, рекорда добычи, инвентаря, станций и истории отдельных рейдов. Эти значения нельзя подменять локальным сохранением в онлайн-профиле.

## P0 — транзакции экономики и серверный инвентарь

В проверенном коде `server/` и `RaidClient.js` нет API покупки, продажи, крафта и улучшения станций. Старые обработчики MenuSystem и LoadoutScreen делали операции локально. В онлайн-режиме покупка/продажа и действия станций теперь недоступны; это временное состояние интерфейса, а не готовая серверная реализация.

Нужен серверный контракт для:

- получения хранилища, снаряжения, вместимости и версии состояния;
- переноса/обмена по уникальному instance ID предмета между допустимыми слотами;
- покупки из серверного каталога и продажи принадлежащего игроку instance ID;
- крафта, изучения чертежа, переработки и улучшения станции;
- выдачи добычи Скраппи по серверному времени.

Названия маршрутов согласовать с backend; UI не вводит фиктивных endpoint-ов. Запрос передаёт намерение и идентификаторы, никогда доверенную цену, награду, уровень или баланс. Ответ возвращает подтверждённое состояние и версию. Нужны атомарность, idempotency key для повторов, проверки владения, количества, вместимости и версии при конкурирующих действиях.

Критерии готовности: два клиента не могут продать один предмет дважды; повтор запроса не выдаёт награду повторно; после перезагрузки баланс и все слоты совпадают; ошибка сети не создаёт локальный успех; полученные из рейда предметы и снаряжение сохраняются сервером.

## P0 — оставшийся разрыв владения снаряжением

Drag-and-drop и Shift+ЛКМ пока меняют клиентский `MenuSystem.loadout/backpack/stash`. Эти операции нельзя считать завершённой онлайн-системой инвентаря. После появления контракта перевести LoadoutScreen на серверные instance ID, pending-состояние и подтверждение версии. Не отправлять локальную демо-коллекцию как доказательство владения.

## P1 — мастерская и таймеры

### Совместимость аугментаций (ARC_MECHANICS.md, раздел 4.3)

Аугментация определяет вместимость, массу, быстрые слоты и допустимые щиты. Текущий клиентский UI фильтрует по категории/slotType; автоматический перенос выбирает свободный совместимый слот, точный перенос допускает обмен. Нужны серверные ограничения для конкретного экземпляра аугментации, включая Cautious/Light Shield, а также обработка уменьшения вместимости без удаления вещей. UI не должен сам назначать ёмкость и разрешать тяжёлый щит в обход серверных правил. До контракта эти расширенные ограничения не считаются реализованными.

Нужен снимок станций: уровень, доступность, изученные рецепты, активное производство, `serverNow`, `readyAt`, состояние получения. Клиент может плавно отображать разницу времён, но достижение нуля не выдаёт предметы и не подтверждает завершение. При reconnect всё сверяется с сервером. Локальная функция `claimScrappyYield` сейчас годится только для офлайн-режима.

## P1 — сводка рейдов

Нужны страницы истории с raid ID, картой, исходом, серверными временами начала/окончания, наградой и потерями. Пока экран «Сводка» показывает только агрегаты `stats` и явно сообщает, что история недоступна. «Оператор» показывает текущую подготовку и экипировку, не дублирует статистику.

Критерии готовности: один рейд встречается один раз; данные совпадают с settlement; пустая история отличается от ошибки/загрузки; нет локального расчёта прибыли и длительности.

## Интеграция UI

После готовности API заменить временные disabled-состояния в MenuSystem/LoadoutScreen. Сохранить фокус, ввод, выделение и прокрутку при ответах сервера. Не пересоздавать сетку во время drag-and-drop. Состояния ошибки и повторного запроса должны быть видимы без потери выбора игрока.

Проверять: авторизация → восстановление сессии → друзья/приглашение → снаряжение → очередь → рейд → settlement → обновлённый аккаунт. Снимки UI-компонентов не заменяют этот сквозной серверный сценарий.
